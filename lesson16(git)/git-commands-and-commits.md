# Git — основные команды и конвенции коммитов

Шпаргалка для повседневной работы: какие команды использовать чаще всего и как правильно называть коммиты.

---

## 1. Основные команды на каждый день

### Проверка состояния

```bash
git status
```
Показывает: какие файлы изменены, какие новые (untracked), что уже добавлено в индекс (staged).

```bash
git diff
```
Построчные изменения в файлах, которые ещё **не** добавлены в индекс (`git add`).

```bash
git diff --staged
```
Построчные изменения в файлах, которые уже добавлены в индекс, но ещё не закоммичены.

---

### Добавление и коммит

```bash
git add .
```
Добавить **все** изменённые/новые файлы в индекс.

```bash
git add имя_файла.go
```
Добавить конкретный файл.

```bash
git commit -m "тип: описание изменений"
```
Зафиксировать снимок состояния проекта.

```bash
git commit -am "тип: описание изменений"
```
`add` + `commit` за один шаг, но **только для уже отслеживаемых файлов** (новые файлы так не добавятся).

---

### Синхронизация с GitHub

```bash
git push
```
Отправить локальные коммиты в удалённый репозиторий.

```bash
git pull
```
Забрать и вмерджить изменения из удалённого репозитория.

```bash
git fetch
```
Скачать изменения с сервера, но **не** применять их к текущим файлам (в отличие от `pull`). Полезно, чтобы сначала посмотреть, что изменилось.

```bash
git clone https://github.com/имя/репозиторий.git
```
Скачать существующий репозиторий целиком (например, на новый компьютер).

---

### История

```bash
git log --oneline
```
Компактная история коммитов.

```bash
git log --oneline --graph --all
```
История со схемой веток — удобно смотреть, как расходились и сливались ветки.

---

### Ветки (branches)

```bash
git branch
```
Показать список веток (текущая помечена `*`).

```bash
git branch название-ветки
```
Создать новую ветку.

```bash
git switch название-ветки
```
Переключиться на ветку.

```bash
git switch -c название-ветки
```
Создать ветку и сразу переключиться на неё (аналог `git checkout -b`).

```bash
git merge название-ветки
```
Влить изменения из указанной ветки в текущую.

---

### Отмена изменений

```bash
git restore имя_файла
```
Откатить несохранённые изменения в файле (вернуть к последнему коммиту).

```bash
git restore --staged имя_файла
```
Убрать файл из индекса (`git add` отменяется), сами изменения в файле остаются.

```bash
git reset --soft HEAD~1
```
Отменить последний коммит, но оставить все изменения в индексе (можно сразу закоммитить заново с другим сообщением).

```bash
git revert <хэш-коммита>
```
Безопасно отменить конкретный коммит, создав новый коммит с обратными изменениями (не переписывает историю — можно использовать даже после `push`).

---

### Временное сохранение (stash)

```bash
git stash
```
Отложить незакоммиченные изменения «в сторону», не создавая коммит (полезно, когда надо срочно переключиться на другую ветку).

```bash
git stash pop
```
Вернуть отложенные изменения обратно.

## 2. Конвенция коммитов (Conventional Commits)

Формат сообщения коммита:

```
type(scope): short description in the imperative mood
```

Пример: `feat(auth): add JWT token validation`

> **Коммиты пишем на английском языке, не на русском.** Это общепринятый стандарт в разработке: над проектом могут работать разработчики из разных стран, а история коммитов — часть открытого кода, который может увидеть кто угодно (работодатель, коллеги, open-source комьюнити). Сообщение вида `feat: добавить эндпоинт` в реальном проекте и на собеседовании будет смотреться непрофессионально — пишите `feat: add endpoint`.

`scope` (в скобках) — необязательная часть, указывает на модуль/пакет, которого касается изменение. Можно опускать: `feat: add JWT token validation`.

### Основные типы

| Тип | Когда использовать | Пример |
|---|---|---|
| `feat` | Новая функциональность | `feat: add user registration` |
| `fix` | Исправление бага | `fix: prevent panic on empty slice` |
| `refactor` | Изменение структуры кода без изменения поведения | `refactor: extract validation logic into a function` |
| `docs` | Изменения только в документации | `docs: update README with run instructions` |
| `style` | Форматирование, отступы, точки с запятой — без изменения логики | `style: apply gofmt across the project` |
| `test` | Добавление или изменение тестов | `test: add tests for ParseInput` |
| `chore` | Рутинные задачи: обновление зависимостей, настройка конфигов, не относится к коду приложения | `chore: update go.mod dependency version` |
| `perf` | Улучшение производительности | `perf: optimize order processing loop` |
| `build` | Изменения в системе сборки, Docker, CI-скриптах | `build: add Dockerfile for the service` |
| `ci` | Изменения в CI/CD конфигурации (GitHub Actions и т.п.) | `ci: run tests on push` |
| `revert` | Откат предыдущего коммита | `revert: revert "feat: add caching"` |

### Правила хорошего коммита

- Один коммит — одно логическое изменение. Не смешивайте фичу и рефакторинг в одном коммите.
- Пишите в повелительном наклонении: **"add"**, а не "added" или "adds".
- Короткое описание — до ~50-72 символов. Если нужно объяснить подробнее — добавьте пустую строку и текст ниже:

```bash
git commit -m "fix: prevent division by zero in calculator" -m "Previously the function panicked on empty input. Added a check before dividing."
```

- Не пишите бессмысленные сообщения вроде `"fix"`, `"update"`, `"asdasd"`, `"правки"` — через месяц никто (включая вас) не поймёт, что там изменилось.

### Частые примеры на практике

```bash
git commit -m "feat: add /users endpoint"
git commit -m "fix: return correct status code on validation error"
git commit -m "refactor: simplify error handling in handlers"
git commit -m "chore: add .gitignore for binaries"
git commit -m "docs: describe project setup in README"
git commit -m "test: add coverage for validator package"
```
